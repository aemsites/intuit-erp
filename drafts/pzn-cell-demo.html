Placement-resolution personalization demo

This page wires Intuit's Decision Engine onto the vendored aem-experimentation plugin's bring-your-own manifest mechanism, using the frozen-API model: Intuit's /pzn endpoint returns CONTENT (a fragment ref, in copyData.pznblock), not a cell name for authoring to map. So the published manifest sheet below only declares a placement id per selector (a key into the Decision Engine's batch response, not a fragment path), and scripts/personalization/byo.js's resolveAudiences issues ONE batched call for every placement on the page and caches what the engine hands back; renderDecision applies THAT cached fragment, never the manifest's own "url" directly.

Try ?audience=anything-else to force the plugin's own upstream QA override to a miss (deterministically shows the default content below, bypassing the engine entirely), or no parameter at all to see the mock engine's pick for each slot (sticky per placement — persisted in pzn-mock-<placement> cookies). Open devtools while loading to confirm there are no console errors.

How this works

The engine owns both WHO (targeting) and WHAT (content) — it returns the resolved fragment ref directly. The manifest sheet only owns selector-to-placement (which DOM slot asks for which placement id); it no longer owns any content mapping. Neither the hero nor the offer slot above carries a data-pzn, data-exp, or personalization-id marker, so this page never touches Intuit's existing pzn.js/exp.js path — it exercises only the plugin's own audience-manifest mechanism.

See drafts/pzn-manifest.json for the published sheet (selector -> placement id), and drafts/fragments/pzn/ for the candidate fragments the demo mock engine can return for each placement.
