Placement-resolution personalization demo

This page wires Intuit's Decision Engine onto the vendored aem-experimentation plugin's decisions-manifest lane — a first-class "engine returns content per slot" mechanism, using the frozen-API model: Intuit's /pzn endpoint returns CONTENT (a fragment ref, in copyData.pznblock), not a cell name for authoring to map. So the published manifest sheet below only declares a placement id per selector (a key into the Decision Engine's batch response, not a fragment path), and scripts/personalization/byo.js's resolveDecisions hook is called ONCE with every row on the page, issues a single batched call for every distinct placement, and returns the resolved fragment straight back to the plugin ({ [selector]: { url } }) — the plugin applies it itself, no cache/lookup needed on this lane.

This lane is off the audience system entirely, so there is no ?audience= override to try here (see the IXP demo for the ?experiment= override instead) — reload with no parameters to see the mock engine's pick for each slot (sticky per placement — persisted in pzn-mock-<placement> cookies); clear/flip those cookies (or just reload enough times) to see the content change. Open devtools while loading to confirm there are no console errors.

How this works

The engine owns both WHO (targeting) and WHAT (content) — it returns the resolved fragment ref directly. The manifest sheet only owns selector-to-placement (which DOM slot asks for which placement id); it no longer owns any content mapping. Neither the hero nor the offer slot above carries a data-pzn, data-exp, or personalization-id marker, so this page never touches Intuit's existing pzn.js/exp.js path — it exercises only the plugin's own decisions-manifest mechanism.

See drafts/pzn-manifest.json for the published sheet (selector -> placement id), and drafts/fragments/pzn/ for the candidate fragments the demo mock engine can return for each placement.
